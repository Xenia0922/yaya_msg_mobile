## 一、P0 致命（5 条）

### P0-1 ⚠️ 已实测更正：单位混用不成立（保留防御性归一）

- **原判断（错）**：HTTP 历史消息 `msgTime` 是**秒**、QChat/NIM 是**毫秒** → 污染轮询水位 → 「聊天流永久冻结」。
  该判断依据是代码里 `chatRows` 的 `>1e12?1:1000` 防御性处理，属**过度推断**。
- **实测（2026-10-03，服务器 + 腾讯云出口代理，3 名在团成员 × 2 个接口）**：
  - `im/api/v1/team/message/list/homeowner` → `msgTime=1790990207579`（**13 位毫秒**）
  - `im/api/v1/team/message/list/all` → 同样 **13 位毫秒**
  - 结论：**HTTP 与 NIM 两侧都是毫秒，不存在单位混用**。
- **保留的改动**：`getMessageTime` 统一走 `toMs`（10 位当秒、13 位原样）——
  无害且更健壮（将来某接口若改回秒级不会再坏），但**它不是「冻结」的根因**。
- **「聊天流冻结」未成立**：用户当初报告的是「小房间全没了 / 成员变 900 / 大小房间错位」
  （根因已定位为**退化到零房间映射的官方目录**，见 RELEASE_NOTES 第 7 项），
  并未报告「新消息不上屏」。把排序/水位推断为用户症状属**误报**。

### P0-2 切房竞态：轮询 / 加载更多 / 失败分支无房间守卫，旧房间数据写进新房间 ✅

- **文件**：`src/screens/FollowedRoomsScreen.tsx:2077-2115`（`refreshRoomMessages`）、`:2045-2074`（`loadMoreRoomMessages`）、`:2034-2040`（`openRoom` 的 catch/finally）、`:1704-1718`（`closeRoom` 未自增 seq）
- **现象**：A 房间轮询/上拉进行中切到 B，A 的响应回来后被 merge 进 B 的列表（**两个成员的消息混在一起**）；A 的失败会把 B 刚加载的消息清空；分页游标 `roomNextTime` 被旧值覆盖 → B 的「加载更多」拉到重复页。
- **根因**：只有 `openRoom` 主路径用了 `roomSeqRef` 做过期丢弃（`:1989`），`refreshRoomMessages` / `loadMoreRoomMessages` 的回调直接 `setState`，闭包锁住发起时的房间；`closeRoom` 也不自增 seq。
- **影响面**：跨成员消息串台、游标错乱（用户点名的「显示错房间 / 旧请求覆盖新房间」）。
- **修复方向**：所有房间请求携带 `{channelId, seq}`，setState 前校验 `seq === roomSeqRef.current && channelId === activeChannelRef.current`；`closeRoom` 自增 seq。

### P0-3 直播流交棒小窗后，回大窗被当作「录播」处理（seek 直播流有原生闪退风险）✅

- **文件**：`src/screens/FollowedRoomsScreen.tsx:1699`（`backTo: { mode: 'vod', ... }` **硬编码**，而同处 `:1692` 已正确使用 `!!cur.isLive`）
- **现象**：房间里看直播 → 点小窗 → 回大窗后：底部切到「录播」tab；出现进度条/倍速/续播等仅录播该有的 UI；**拖动进度条 seek 直播流** —— 按 `playerStore.ts:74-84` 注释「rtmp/直播流 seek 会原生闪退」，有崩溃风险。
- **根因**：`handleRoomMiniPlayer` 漏判 `cur.isLive`，`backTo.mode` 写死 `'vod'`；`MiniPlayer.backToFull` 原样透传给 `MediaScreen`，后者据此 `isLive=false` 开 `rate/resume` 并 `switchTab('vod')`。
- **影响面**：所有「房间直播 → 小窗 → 回全屏」用户；竖屏成员直播（rtmp/flv）最易触发。
- **修复方向**：`backTo.mode` 改为 `cur.isLive ? 'live' : 'vod'`；`MediaScreen` 侧对 `playUrl` 再做一次 live/vod 兜底判定。

### P0-4 播放器换线被误判为「被别的页面顶替」→ 直接关闭播放器 ✅

- **文件**：`src/player/PlayerScreen.tsx:109-115`（判定 `storeUrl !== sourceUrl`）；触发源 `src/player/core/PlayerCore.tsx:141-142`（`kernelError → nextCandidate()`）、`src/player/store/playerStore.ts:174-190`
- **现象**：多线路源（MediaScreen 的 `urls`、B 站多清晰度/多线路）**首条线路失败时，本应静默切下一条，实际整个播放器被关闭、退回列表页** —— 用户看到「莫名其妙掉出播放器」。
- **根因**：跨页互斥用「本组件声明的 `source.url`」与「store 里的 `source.url`」做不等比较判断「被顶替」；而内核自动换线会把 `store.source.url` 改成候选地址，页面 prop 不变 → **同一页面内部的换线被误判为跨页顶替**，触发 `onClose`。
- **影响面**：所有传多个 `urls` 且带 `onClose` 的播放器页（MediaScreen / BilibiliLiveScreen / VideoLibraryScreen / OpenLiveScreen）。「失败自动恢复」这条路本身被废掉。
- **修复方向**：跨页顶替改为显式事件判定（store 记录 `openToken`/`pageId`），而不是比对 url。

### P0-5 网络层外部 signal 会让超时机制彻底失效，请求可无限挂起 ✅

- **文件**：`src/utils/network.ts:131`（`signal: options.signal ?? controller.signal`），配套 `:103-114` 的 `extAbort` 联动与 `:105` 的 `setTimeout(() => controller.abort())`
- **现象**：`requestJson` 传 `options.signal` 时，`fetch` 用的是**外部 signal**，而超时定时器只 abort 内部 controller —— 该 controller 的 signal 从未挂到 fetch 上，**超时完全失效，请求可永久 pending**，loading 永不结束。
- **根因**：内部超时与外部取消被错误实现成「二选一」，而 `:106` 注释声称「外部中止时联动内部 controller（否则 timeout 形同虚设）」—— 注释与实现相反。
- **影响面**：当前仓库内无调用方传 `signal`，属**未引爆**的 P0；一旦新增调用方即成为线上致命。
- **修复方向**：`fetch` 永远用 `controller.signal`，外部 signal 仅通过 `extAbort` 联动内部 controller（同文件 `fetchWithTimeout` 的写法才是正确的）。
