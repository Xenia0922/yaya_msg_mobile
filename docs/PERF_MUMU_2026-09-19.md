# MuMu 实机性能实测报告（2026-09-19）

设备：MuMu 模拟器，伪装 `SM-S938U`（三星 S25 Ultra），Android 35，x86_64，1080×1920 @480dpi
被测包：`com.yk1z.yayamsg` v2.7.5（**release 包**，`flags=0x0` 无 DEBUGGABLE，数据可比）
方法：`dumpsys gfxinfo` / `/proc/<tid>/schedstat` 增量 / `simpleperf` / `simpleperf` callgraph / `kill -3` 线程栈 / AsyncStorage 与运行时日志直读

## 一、总账：空闲即吃 129% CPU

`dumpsys cpuinfo`（独立于我的采样，两次一致）：

```
129%  4923/com.yk1z.yayamsg: 111% user + 18% kernel / faults: 10,566,036 minor
 32%  TOTAL（4 核 → 129% ≈ 1.3 个核心）
```

**App 在完全没触碰、停在设置页的情况下，稳定烧 1.3 个核心**，累计 1056 万次缺页（minor fault = 访问新分配的页 → 持续大量内存分配）。

线程级增量（6 秒采样，按累计 CPU 增量）：

| 线程 | CPU | 说明 |
|---|---|---|
| **mqt_v_js** | **81.2%** | RN 的 JS 线程 |
| HeapTaskDaemon | 18.5% | ART（Java/Kotlin）GC |
| **hades** | **14.8%** | **Hermes 自己的 GC 线程**（`hades` 是 Hermes GC 代号；已用 `/proc/maps` 偏移映射确认它属于 `libhermesvm.so`） |
| om.yk1z.yayamsg (main) | 1.6% | UI 线程 |
| mqt_v_native | 0.7% | RN 原生模块线程 |
| OkHttp / Fresco | **0%** | 网络与图片解码**全空闲** |

即：**JS 执行 81% + Hermes GC 15% + ART GC 18.5%**。堆栈采样 100% 落在 `libhermesvm.so`，且极其扁平（无单一热点函数），同时 `memcpy`/`memset`/`do_user_addr_fault` 占比高 → 典型的**疯狂分配 + GC**，不是某个计算热点。

### 关键分诊（逐条排除）

| 假设 | 实测 | 结论 |
|---|---|---|
| 网络轮询 | OkHttp 线程 CPU = **0%**；logcat 5 秒仅 11 行且无本应用输出 | ❌ 排除 |
| 日志刷屏 | 同上 | ❌ 排除 |
| AsyncStorage 持续写入 | `RKStorage` 12 秒内 size/mtime **完全不变**；运行时日志 10 分钟**零新增** | ❌ 排除 |
| 重渲染死循环 | 静置 10 秒 `dumpsys gfxinfo` = **Total frames rendered: 0** | ❌ 排除（UI 完全没在渲染） |
| 某个 `Animated.loop` | 全仓 7 处 `Animated.loop` **全部** `useNativeDriver: true` | ❌ 排除 |
| 页面内容相关 | 直播网格 76% / 设置页 69% / 主页 64% / 房间页 72% —— **每一页都一样** | ❌ 排除页面级 |
| 后台停不停 | 前台 82% / **按 HOME 切后台 82%** | 是**常驻**的，与视图层无关 |
| 何时开始 | 冷启动后 **3 秒 = 0%，8 秒 = 83%** 并稳定 | 在**初始数据加载完成后**才启动 |
| 自造死循环代码 | `while(true)`/`for(;;)`/`setImmediate`/`requestAnimationFrame` 循环/无界 while **均无**（0 命中） | 未在源码中找到明显死循环 |
| 环境/包问题 | release 包；`hades` + `mqt_v_js` 都在 `libhermesvm.so` | 真实 JS 侧问题 |

**结论：JS 线程存在一个「与页面无关、初始数据加载完成后启动、切后台也不停、不渲染、不联网、不写盘、不打日志」的纯计算+高分配循环，让 App 空闲即耗 1.3 核。**

> 精确定位到具体 JS 函数需要 Hermes 级采样（`SamplingProfiler`）或带符号的 `libhermesvm.so`；release 包两者都没有（bundle 是 Hermes 字节码 `c61fbc03`，无法改代码二分）。**下一步最省事的验证路径**：在 debug 包上跑 Hermes CPU Profile（可直接给出 JS 函数名与火焰图）。

## 二、直播/录播网格滑动卡顿：图片是真凶（已定位到根因）

同一手势、同一设备、同一时段，只换页面：

| 页面 | 帧耗时中位数 | Slow bitmap uploads | 判读 |
|---|---|---|---|
| **录播/直播双列网格** | **48ms**（≈21 FPS） | 1 | 3× 差 |
| 设置页（几乎无图） | **16ms**（= 60 FPS 满帧） | 0 | 基线 |
| 用户手动 fling（原始投诉） | **105ms**，Janky **209/209 = 100%**，`Slow bitmap uploads 209/209` | 209 | 最差 |

GPU 完全无辜：`50th gpu percentile: 1ms`（100% 的帧）。**瓶颈全在 CPU 侧的位图解码/上传。**

### 根因：`thumbUrl()` 从未生效 —— 每张封面都在下原图

`src/utils/imageThumb.ts` 给 48 图床 URL 追加 `?imageView&thumbnail=<w>x0`，但**服务端完全忽略该参数**。实测（同一张图，逐一试语法）：

```
原图                                            783,734 bytes
?imageView&thumbnail=500x0                      783,734 bytes  ← 一模一样
?imageView&thumbnail=200x0                      783,734 bytes
?x-oss-process=image/resize,w_500               783,734 bytes
?imageView2/2/w/500                             783,734 bytes
?imageMogr2/thumbnail/500x                      783,734 bytes
?imageView/2/w/500                              783,734 bytes
?w=500                                          783,734 bytes
```

换域名同样无效：`source.48.cn` 与 `source3.48.cn` 都返回 783,734；`pfile.48.cn` 直接 404。

**8 张真实封面抽样**（说明量级）：

| # | 字节 | 像素 |
|---|---|---|
| 1 | 783,734 | 828×1104 |
| 2 | 548,068 | 828×622 |
| 3 | **1,380,698** | 828×1472 |
| 4 | 912,968 | 828×1104 |
| 5 | 445,268 | 828×764 |
| 6 | 927,336 | 828×1104 |
| 7 | 836,852 | 832×1110 |
| 8 | 356,819 | 829×466 |

平均 **~0.78 MB/张**。双列网格每张卡在 1080px 屏（480dpi）上显示宽度仅约 480px，却按 828px 解码：RGBA 纹理 = 828×1104×4 = **3.66 MB/张**，实际是 **1.7× 过采样**。滑动时同时有新卡进视口 → 下载 + 解码 + 上传全挤在滚动帧里。

**这条是「滑动卡顿」的直接、可复现、可量化的原因。**

## 三、附带确认的两项

### 3.1 `pa` 签名走常驻隐藏 WebView（Hermes 无 WebAssembly）

运行时日志：

```
[initWasm] Native WASM unavailable (Hermes), falling back to WebView signer:
当前运行环境缺少 WebAssembly 支持
```

`App.tsx:718` **常驻挂载** `<WebViewSigner />`：一个 1×1、`opacity:0.01` 的隐藏 WebView，内部用 70KB base64 注入 WASM（`src/auth/wasmBase64.ts` + `wasmGlueSource.ts`）来算每个请求的 `pa` 签名。这解释了进程中出现的 Chromium 线程（`ve.bilibili.com`、`-data.pages.dev`）。

本身不是死循环（请求-响应式，逐级 `waitForMount`/`waitForReady` 都有超时），但它意味着：**App 全程多背一个 WebView 进程 + WebAssembly 运行时**，是常驻内存与功耗的一部分。若要省，只能把 `pa` 用纯 JS 实现或换非 Hermes 引擎。

### 3.2 首页 3 处「列表内逐卡玻璃」（本轮已修，见下）

`HomeScreen` 的公演直播列表 / 快捷入口 / 横向工具条原本逐卡 `GlassSurface`，违反项目铁律「列表/网格里绝不要逐卡 GlassSurface」。已在提交 `7f83d48` 改为实底圆角。

## 四、修复方案（按性价比排序）

| 优先级 | 项 | 做法 | 预期 |
|---|---|---|---|
| **P0** | **图片解码/上传** | ① 网格卡显式给定宽高（让 Fresco 按目标尺寸解码，而非 828px）；② 或换 `expo-image`（原生侧降采样 + 内存/磁盘缓存）；③ 网格 `getItemLayout` + 收紧 `windowSize`/`initialNumToRender`，减少同时在飞的解码数 | 帧耗时 48ms → 接近无图页的 16ms |
| **P0** | **JS 线程空闲 129%** | 需先定位：**debug 包 + Hermes CPU Profile** 拿到函数名与火焰图，再定点修 | 省 ~1.3 核 + 消除卡顿根因 |
| P2 | `thumbUrl` 语义 | 既然参数无效：要么删掉这个无用 query（还能让 HTTP 缓存与其他客户端共用），要么换成真正生效的降采样方案 | 减少一次无用请求变体 |
| P2 | 常驻 WebView 签名器 | 评估纯 JS 实现 `pa`，去掉常驻 WebView | 省内存/功耗 |

# ★ 后续：根因已定位并修复（同日下午）

用 **debug 包 + Hermes CDP CPU Profile** 拿到了函数级火焰图，把第一节那个
「JS 线程空闲烧 81%、无网络/无日志/不渲染」的失控循环彻底定位了。

## 定位过程

release 的 `libhermesvm.so` 不含采样分析器（相关方法在 `libhermestooling.so`，只有 debug 变体有），
所以出了 debug 包。踩到两个坑后跑通：

1. **worklets 版本不匹配**：`expo/node_modules/react-native-worklets` 里有一份多余的 **0.8.3**，
   而原生库是 0.7.4 → Babel 插件解析到 0.8.3 → 启动即
   `WorkletsError: Mismatch between JavaScript code version and Worklets Babel plugin version`。
   把它挪走让解析回落到根部 0.7.4 即解决（**只动 node_modules，不改仓库**）。
2. **Hermes inspector 不支持 `Profiler.enable`**（返回 -32601），
   但 `Profiler.start` / `Profiler.stop` **直接可用** → 用 CDP 直接采样即可。

```
adb reverse tcp:8081 tcp:8081
curl http://127.0.0.1:8081/json/list      # → webSocketDebuggerUrl
# CDP: Runtime.enable → Profiler.setSamplingInterval → Profiler.start → 等 → Profiler.stop
```

## Profile 结果（12s 采样）

| 占比 | 函数 |
|---|---|
| 39.9% | `[root]`（采样归属开销） |
| **34.4%** | **`[GC Young Gen]`** ← 分配churn导致的年轻代 GC |
| **21.6%** | **`[Native] jsonParse`** ← `JSON.parse` 在狂转 |
| 1.0% | `[Host Function] multiGet`（AsyncStorage） |

调用链（Hermes 会把原生函数名字加上 `[Native] `/`[Host Function] ` 前缀）：

```
jsonParse
  └ ?anon_0_  @ index.bundle:353857
multiGet → getItem @ index.bundle:193359
      └ ?anon_0_ @ index.bundle:353854
          └ loadR2Music @ index.bundle:353844
              └ prefetchR2Music @ index.bundle:353898
```

## 根因：`src/api/r2Music.ts` 的自递归死循环

```ts
export async function loadR2Music(force = false) {
  if (!force) {
    const raw = await AsyncStorage.getItem(CACHE_KEY);   // 读 1MB
    const parsed = JSON.parse(raw);                      // 解析 1MB  ← 21.6% CPU
    if (Array.isArray(parsed.list) && parsed.list.length) {
      if (parsed.t && Date.now() - parsed.t >= CACHE_TTL) {
        prefetchR2Music().catch(() => {});               // → 又调 loadR2Music(false)
      }
      return parsed.list;                                // ← 但这里就返回了，从不走网络
    }
  }
  ...
}
```

- 缓存过期（>24h）→ 起一次「后台刷新」；
- 那个「刷新」就是 `prefetchR2Music()` → `loadR2Music(false)`，**又命中同一份过期缓存**、
  又直接 `return parsed.list` —— **永远不真正发网络请求**，缓存永远过期；
- 于是每命中一次过期缓存就再起一次刷新 → **无限递归**。

设备实测：`yaya_r2_music_cache_v1` = 1,006,542 字符 / 1560 首，`t` 距今 **44.5 小时**（已过期）
→ 每次冷启动必然启动这个循环。这也解释了为什么全程**没有网络活动、没有日志、不渲染**。

## 修复

把「真正拉取」与「对外读取」拆开：

- 新增 `fetchR2MusicAndCache()`：只负责拉取 + 写缓存 + 失败回退旧缓存（模块级 in-flight 去重）；
- 新增 `refreshR2MusicInBackground()`：后台刷新走 **`fetchR2MusicAndCache()`**（不再回调 `loadR2Music`），
  并用 `refreshing` 标志 + `lastRefreshAttempt` 最小重试间隔（10 分钟）双保险；
- `loadR2Music` 命中过期缓存时只调 `refreshR2MusicInBackground()`，行为与原来一致（先返回缓存秒开）。

顺带核查了 `officialSiteMusic`（同款 24h TTL）—— 它是**只在未过期时返回缓存**、过期就走网络，
**没有**这个递归问题。

## 修复效果（同一设备、静置不操作）

| 指标 | 修复前 | 修复后 | 改善 |
|---|---|---|---|
| **进程总 CPU** | **129%** | **7%** | **18×** |
| JS 线程 `mqt_v_js` | 81% | **5.7%** | 14× |
| Hermes GC（`hades`） | 15% | ~0 | 消除 |
| ART GC（`HeapTaskDaemon`） | 18.5% | ~0 | 消除 |
| **minor page faults** | **10,566,036** | **44,451** | **238×** |

**验证方式（端到端）**：代码没动，只把设备上那个过期的
`yaya_r2_music_cache_v1` 删掉 → JS CPU 立刻从 **80% → 4~5%**，三测一致。
（注：debug 包数值，release 只会更低。）

> 对已有用户的影响：修复后的代码在缓存过期时只会**尝试刷新一次**并写入新缓存，
> 不会再递归。即使刷新失败（网络不通）也有 10 分钟节流兜底，不会再自旋。
